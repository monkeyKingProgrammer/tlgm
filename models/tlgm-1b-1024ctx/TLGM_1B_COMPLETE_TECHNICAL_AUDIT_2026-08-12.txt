1. EXECUTIVE VERDICT
====================

TLGM-1B-1024 is a real, independently implemented, decoder-only causal
language model trained from random initialization. It contains no attention,
QKV projections, Transformer blocks, recurrent state, convolution, state-space
layer, imported model weights, or KV cache. The completed base model has
1,015,592,960 registered parameters, a 1,024-token context, an 8,192-entry
byte-level BPE vocabulary, and 27 global mixing blocks.

The corrected production pretraining run completed successfully. It processed
20,000,014,336 input token positions, corresponding to 19,980,483,072 actual
next-token targets, in 231.70 measured GPU hours. Broad chat SFT, repair SFT,
and polish SFT also completed. A new large reasoning continuation is currently
running from the completed chat checkpoint.

The model and trainer pass all 14 current automated tests. The audit found no
remaining double-shift error, no observed future-token leakage, no parameter
shape mismatch, and no evidence that the active process loaded the wrong base
checkpoint.

However, the project is not production-ready. Several silent issues can reduce
quality or operational reliability without throwing an exception:

  * overlength multi-turn SFT records retain the first assistant response and
    can discard all later turns;
  * overlength math solutions retain their reasoning beginning but commonly
    lose the final answer and EOS target;
  * every resumable checkpoint stores model weights as FP16 even though the
    live optimizer maintains FP32 master parameters and the current stage uses
    BF16 autocast;
  * the active reasoning run is a nohup background process, while the installed
    systemd service is inactive and still points to the old full pipeline;
  * 28,283,904 registered parameters are permanently masked upper-triangular
    entries that never affect a forward pass;
  * validation and token-accounting labels can be misunderstood;
  * dataset revisions, hashes, cross-source deduplication, and benchmark
    decontamination are incomplete.

The completed pre-reasoning benchmark is useful as an internal baseline. It is
not directly interchangeable with official Open LLM Leaderboard numbers because
the prompting and scoring protocols differ. On comparable commonsense tasks,
TLGM is materially behind established Transformer models around 1B parameters.
The largest reason is training-data scale: TLGM used 20B pretraining token
positions, versus 300B for Pythia-1B, 3T for TinyLlama-1.1B, up to 9T for
Llama-3.2-1B, and 11T for SmolLM2-1.7B. Architecture and post-training quality
also matter; token count alone does not explain the entire gap.

3. SEVERITY-RANKED CODE AND PIPELINE FINDINGS
=============================================

3.1 HIGH: Overlength multi-turn SFT loses later turns
-----------------------------------------------------

Evidence:
  tlgm/dataset.py:148-161

The truncation code finds the first supervised assistant token in the entire
conversation. If the flattened conversation exceeds 1,024 tokens, it keeps a
limited prompt region before that first assistant response and then keeps the
beginning of supervised text from that point. It does not preferentially keep
the latest user turn or latest assistant turn.

Impact:

  * long UltraChat conversations can train only their first response;
  * later conversation turns, follow-up questions, corrections, and contextual
    behavior can be discarded;
  * the dataset may report one multi-turn example while the effective training
    sample contains only its earliest exchange.

Recommended correction:

  Split each conversation into one training sample per assistant turn. For each
  target assistant turn, retain as much immediately preceding dialogue as fits,
  mask all prompt tokens, and supervise that one response plus EOS. This gives
  explicit coverage to every assistant turn and avoids ambiguous truncation.

This correction changes the SFT sample stream but not model shapes. It should be
implemented before a future SFT run, not injected into the currently running
process.


3.2 HIGH: Long math traces often lose the final answer and EOS
--------------------------------------------------------------

Evidence:
  tlgm/dataset.py:148-161
  scripts/prepare_reasoning_sft.py:58-67

For a one-turn math record longer than context, the loader now preserves the
question tail and beginning of the solution. This is better than preserving an
orphaned solution tail, but the final answer and EOS are omitted when the
solution exceeds the remaining budget.

This is especially important for OpenR1-Math-220k. Its official card says
solutions were generated with limits as high as 16K tokens. A 1,024-token model
cannot consume many of these traces in full.

Impact:

  * the model learns how to begin long reasoning but not necessarily how to
    terminate it or state the verified result;
  * EOS training is absent on truncated samples;
  * long DeepSeek-R1 traces can consume substantial training weight while only
    a small prefix is usable;
  * the nominal example count overstates complete answer coverage.

Recommended correction:

  Filter or transform before training. Prefer verified solutions that fit the
  model context. For long records, create a compact target containing a concise
  rationale and the verified final answer. At minimum, reserve a tail budget for
  the boxed/final answer and EOS while preserving a reasoning prefix. Record
  exact truncation statistics in the manifest.


3.3 HIGH: Checkpoint resumes quantize FP32 master weights through FP16
---------------------------------------------------------------------

Evidence:
  tlgm/trainer.py:115-136
  tlgm/trainer.py:194-213

The model is created in FP32 and moved to CUDA. Autocast controls operation
precision, but does not convert the persistent model parameters. The optimizer
therefore updates FP32 master parameters. Checkpoint saving explicitly converts
every model tensor to FP16:

  v.detach().half().cpu()

On resume or stage transition, those FP16 values are copied back into FP32
parameters. The lost mantissa precision cannot be recovered. The current BF16
reasoning stage also stores its best model as FP16, not BF16.

Impact:

  * each process restart or stage transition applies another FP16 rounding of
    the master weights;
  * BF16's wider exponent range is not preserved in checkpoint storage;
  * a rare weight outside FP16's finite range could become infinity even though
    it is representable in BF16;
  * exact resume is impossible even when sampler and RNG state are restored.

The live run is not modified by each save because conversion is performed on a
copy. The degradation occurs when loading a saved checkpoint.

Recommended correction:

  Store resumable model weights in FP32, or explicitly train persistent model
  weights in BF16 and store BF16. Keep a separate smaller FP16 inference export
  if disk size matters. Record checkpoint dtype in metadata and add a test that
  save/load is numerically exact for the chosen master dtype.


3.4 HIGH: Active reasoning training is not reboot-persistent
------------------------------------------------------------

Measured state at audit:

  active Python PID: 1431368
  launch method: nohup background shell
  tlgm1b-training.service: inactive/dead
  service restart count from earlier runs: 22
  installed service ExecStart: run_tlgm_1b_full_pipeline.sh

Evidence:
  run_reasoning_improvement_3day.sh:1-11
  ops/tlgm1b-training.service:1-23

The old service does not launch the new reasoning pipeline. If the workstation
reboots, the current nohup process terminates. Even if the old service starts,
it walks the completed pretrain/chat/repair/polish pipeline and does not resume
the reasoning config.

There is also no SIGINT/SIGTERM handler that forces a final checkpoint. With a
500-step save interval and about 2.58 seconds/step, a shutdown can lose up to
about 21.5 minutes of work.

Recommended correction:

  Create a dedicated systemd unit for run_reasoning_improvement_3day.sh or the
  exact reasoning train command, with network-online ordering, Restart=on-failure,
  UPS-compatible normal shutdown, and a trainer signal handler that atomically
  saves before exiting. Do not disable the UPS shutdown service.


3.5 MEDIUM: Registered parameter count includes 28.28M inactive values
------------------------------------------------------------------------

Evidence:
  tlgm/causal_linear.py:15-28

Each 1,024 x 1,024 sequence matrix is stored as a dense trainable parameter and
multiplied by a lower-triangular mask at every forward pass. The strictly upper
triangle can never affect output. There are two such matrices in each of 27
blocks:

  inactive values per matrix = 1,024 * 1,023 / 2 = 523,776
  matrices                 = 2 * 27 = 54
  inactive parameters      = 28,283,904
  fraction of registered total = 2.785%

These entries receive zero task gradient but still receive AdamW bookkeeping
and decoupled weight decay because their full tensor has a gradient object.

Nominal registered parameters: 1,015,592,960
Forward-active parameters:       987,309,056

Approximate training-state waste for these values, using FP32 parameter,
gradient, and two Adam states, is about 452.5 MB decimal (431.5 MiB), excluding
temporary buffers.

This does not make the model incorrect, but it inflates model size and wastes
memory/checkpoint space. A packed triangular parameterization would remove the
dead values while retaining the architecture.


3.6 MEDIUM: Current reasoning corpus contains substantial source overlap
------------------------------------------------------------------------

The 200,000-example existing-chat source comes from a 217,172-row mixture
containing targeted examples, Alpaca, Dolly, and up to 150,000 UltraChat rows.
Because the first 200,000 rows are used, approximately 132,828 of them are from
UltraChat. The new reasoning mix separately adds 200,000 shuffled UltraChat
rows from a train split containing 207,865 examples.

Therefore, a large overlap is structurally expected. Exact canonical duplicate
count has not been recorded, and multi-turn truncation differences can make
line-level hashes miss semantically duplicated records.

Impact:

  * UltraChat receives more weight than the manifest names suggest;
  * nominal 1.61M examples overstates unique-example count;
  * repeated generic assistant style may displace other knowledge or reasoning
    data.

Recommended correction:

  Add stable content hashes over normalized role/content sequences, deduplicate
  globally, and publish unique counts and overlap matrices by source.


3.7 MEDIUM: Pretraining validation is not representative of the full mix
------------------------------------------------------------------------

Evidence:
  scripts/prepare_pretrain20b_tokens.py:129-202
  tlgm/trainer.py:152-163

The 20B token binary is written as four contiguous source regions. Validation
is the final 10,000 windows of the whole binary. Consequently, pretraining
validation comes entirely from the last source, FineWeb-Edu sample-10BT, rather
than from a stratified sample of all four sources.

The final pretraining validation loss of 2.5619 and perplexity 12.96 are valid
for that fixed FineWeb-Edu slice under this tokenizer. They are not a balanced
validation metric for the complete 40/25/20/15 mixture.

Recommended correction:

  Build immutable held-out shards per source, exclude them before constructing
  training data, and report both per-source and weighted validation.


3.8 MEDIUM: Reasoning best-model selection evaluates only 128 examples
------------------------------------------------------------------------

Configuration:

  holdout_samples: 5,000
  eval_batches: 32
  validation batch size: 4

The validation loader is deterministic and evaluation stops after 32 batches.
Thus every validation event measures only the same first 128 held-out examples,
not all 5,000. At step 3,000 this represented 55,903 supervised target tokens.

Impact:

  * best-checkpoint choice may reflect a narrow fixed subset;
  * rare tasks and sources in the remaining holdout have no effect;
  * validation can look smooth while regressions elsewhere remain invisible.

Recommended correction:

  Evaluate the full holdout less often, rotate deterministic subsets by event,
  or stratify a fixed validation sample by source and task. Store source-level
  losses, not only one aggregate.


3.9 MEDIUM: Token totals require careful interpretation
-------------------------------------------------------

Pretraining windows contain 1,024 input positions, but causal loss predicts
only positions 1 through 1,023. The trainer correctly records both counters:

  pretraining input positions: 20,000,014,336
  pretraining supervised targets: 19,980,483,072

The difference is 19,531,264 positions, exactly one non-target input position
per processed sequence.

For SFT, total_seen_tokens includes padding. It is a compute-budget measure,
not a count of meaningful text tokens. total_supervised_tokens is the better
measure of assistant-target training.

The phrase "trained on 20B tokens" is acceptable as an input-position budget,
but the report and model card should always expose both counters.


3.10 MEDIUM: No corpus revision pins, global checksums, or decontamination
--------------------------------------------------------------------------

Evidence:
  scripts/prepare_pretrain20b_tokens.py
  scripts/prepare_reasoning_sft.py

Hugging Face dataset names and configurations are specified, but commit
revisions are not. The 40GB pretraining binary has no recorded SHA-256 hash.
The source builders take the beginning of streaming datasets rather than a
revision-pinned randomized document sample. No global deduplication is applied
across FineWeb-derived sources, Wikipedia, chat datasets, and synthetic math.

No benchmark decontamination is performed. OpenMathInstruct-2 is derived from
GSM8K and MATH training problems and publishes a contamination explorer for
related test sets. The current reasoning mix also explicitly uses ARC-Easy,
ARC-Challenge, OpenBookQA, and BoolQ training splits. These are not the same
splits used by the current benchmark, but future scores after task-specific SFT
must be labeled as task-adapted, not clean base-model zero-shot results.

Recommended correction:

  Pin revisions, hash every final artifact, record selected source row IDs,
  deduplicate normalized text, and run n-gram or MinHash decontamination against
  every evaluation set before training.


3.11 MEDIUM: AdamW weight decay is applied to norms and biases
-------------------------------------------------------------

Evidence:
  tlgm/trainer.py:208

One optimizer group contains all parameters. Therefore weight decay is applied
to LayerNorm scale/bias, linear biases, embedding values, and useful/inactive
sequence weights alike. Common LLM practice excludes normalization and bias
parameters from decay.

This is not a runtime error, and changing it during an active run would change
optimizer semantics. Future runs should use explicit decay/no-decay parameter
groups and test group membership.


3.12 MEDIUM: One full checkpoint has no resumable fallback
----------------------------------------------------------

The one-checkpoint policy saves disk but creates a single point of failure.
Atomic replacement protects against many interrupted writes, but there is no
fsync and no previous full optimizer checkpoint. The separate best checkpoint
contains model weights only and cannot exactly resume optimizer/sampler state.

The full checkpoint is about 10.19 GB decimal. A robust compromise is one
current checkpoint plus one previous checkpoint, or periodic model-only
archives with one current and one previous full resume state.


3.13 LOW: Chat inference does not use mixed precision
-----------------------------------------------------

Evidence:
  chat_cli.py:23-30
  tlgm/generation.py:21-35

Checkpoint values are loaded into a newly constructed FP32 model, and chat
generation has no autocast context. The benchmark code does use BF16/FP16
autocast. Chat therefore consumes more memory and is slower than necessary.

Use BF16 weights or BF16 autocast on Blackwell. Validate output stability before
making BF16 the default.


3.14 LOW: Sliding context resets absolute positions
---------------------------------------------------

Evidence:
  tlgm/generation.py:25-27
  tlgm/embeddings.py:12-15

After history exceeds 1,024 tokens, generation keeps the newest 1,024 IDs and
renumbers them from absolute position zero. This is unavoidable with the
current simple sliding implementation but differs from how those tokens were
positioned before truncation. Learned absolute position embeddings and
position-specific mixers make this discontinuity more significant than for a
relative-position model.


3.15 LOW: Logs append across retries and the pretrain JSONL contains NUL bytes
-----------------------------------------------------------------------------

The trainer always opens loss logs in append mode. The pretraining loss file
contains approximately 2.92 million NUL bytes and 316,945 lines, more than one
clean 305,176-step run plus validation would require. The final records are
readable, but simple grep can classify the file as binary and abandoned-run
records can be mixed with the production run.

Every run should have a run ID and separate file, or append a formal session
record. Add a JSONL validator and compact historical logs after completion.


3.16 LOW: Dependency versions are not reproducibly pinned

==============================

4.3 Forward path
----------------

For token IDs X of shape [B,N], N <= 1024:

  1. Token embedding E_token[X] gives [B,N,2048].
  2. Learned absolute positions E_pos[0:N] are added.
  3. Dropout is applied; configured dropout is zero.
  4. Input projection is identity because embed_dim == model_dim.
  5. A shared per-token MLP applies:

       Linear(2048 -> 8192)
       GELU
       Dropout(0)
       Linear(8192 -> 2048)
       LayerNorm(2048)

     This stage does not mix sequence positions and has no residual connection.

  6. Twenty-seven GlobalMixingBlocks run sequentially.
  7. Final LayerNorm is applied.
  8. Hidden states are projected to 8,192 vocabulary logits using the token
     embedding matrix transposed. There is no output bias.


4.4 GlobalMixingBlock
---------------------

Each block has two residual branches.

Token/sequence branch:

  y = LayerNorm(x)
  y = L2(GELU(L1(y)))
  x = x + y

L1 and L2 each use a learned 1,024 x 1,024 matrix shared across all 2,048
feature channels. At runtime only the lower triangle is active:

  y[b,n,d] = bias[n] + sum over j<=n of weight[n,j] * x[b,j,d]

Feature branch:

  y = LayerNorm(x)
  y = Linear(8192 -> 2048)(Dropout(GELU(Linear(2048 -> 8192)(y))))
  x = x + y

There is no content-dependent selection of earlier positions. Every feature
channel uses the same learned position-mixing matrix in a given sequence layer.


4.5 Initialization
------------------

General Linear/Embedding weights use Normal(0, 0.02). Biases are zero and
LayerNorm scales are one. Sequence mixer L1 is Xavier uniform. L2's Xavier gain
is divided by sqrt(2*27). The output projection of every feature MLP uses
standard deviation 0.02/sqrt(54). This stabilizes residual accumulation.


4.6 Causality and objective
---------------------------

The lower-triangular mask prevents position n from reading j>n. Automated tests
change future input tokens and confirm that earlier logits remain identical.

Loss is standard one-token causal cross entropy:

  logits[:, 0:N-1] predict labels[:, 1:N]

SFT sets prompt and assistant-prefix labels to -100, so only assistant content
and EOS are supervised when retained.


4.7 Computational characteristics
----------------------------------

Advantages:

  * simple causal mechanism;
  * no attention softmax;
  * no QKV projections;
  * global receptive field in every block;
  * fixed memory independent of a KV cache during decoding;
  * exact causal structure is easy to test.

Disadvantages:

  * sequence mixing is O(N^2 * D) per mixer and is repeated twice per block;
  * feature MLPs dominate a large part of compute;
  * no content-dependent routing means a token cannot dynamically choose which
    prior token to retrieve;
  * learned matrices are tied to absolute positions and exactly 1,024 context;
  * no KV cache means every generated token recomputes the retained context;
  * autoregressive generation before context saturation grows much more
    expensive than cached Transformer decoding;
  * the architecture cannot be extended to 2K/4K merely by changing one config
    value because sequence matrices and position embeddings change shape.


5. TOKENIZER
============

Type: Hugging Face tokenizers ByteLevelBPETokenizer
Vocabulary size: 8,192
Special IDs:

  0 <pad>
  1 <bos>
  2 <eos>
  3 <unk>

Tokenizer files:

  tokenizer/vocab.json
  SHA-256 E4C5DADFA59E1059324269132827F4C548F3411C5409A90BDD0FEF0212A119D3

  tokenizer/merges.txt
  SHA-256 4FF5482BA80A329A4F5FB50E5179460F3C97FE7DFE814AB4C0EB8C1183EADCE4

The tokenizer was trained from scratch, not copied from another language
model. The utility extracts up to 200,000 records from the earlier 120M
project's prepared pretraining JSONL and trains byte-level BPE with minimum
merge frequency two.

The 8K vocabulary reduces embedding/output parameters and output softmax cost,
but tokenizes English less compactly than common 32K-150K vocabularies. Thus
1,024 TLGM tokens generally represent less text than 1,024 tokens in several
comparison models, and raw training token counts are tokenizer-dependent.


6. PRETRAINING DATA
===================

The final binary contains exactly 20,000,000,000 uint16 tokenizer IDs and is
40,000,000,000 bytes (37.25 GiB). Documents are wrapped in BOS/EOS when they fit
within source quotas. The model was initialized randomly.

Source mixture:

  40% / 8.0B tokens
  HuggingFaceTB/smollm-corpus, fineweb-edu-dedup
  Deduplicated educationally filtered English web text.

  25% / 5.0B tokens
  HuggingFaceTB/smollm-corpus, cosmopedia-v2
  Synthetic educational textbooks, articles, blogs, and stories generated by
  Mixtral-8x7B-Instruct from diverse seed material.

  20% / 4.0B tokens
  wikimedia/wikipedia, 20231101.en
  Cleaned English Wikipedia article text from the November 2023 dump.

  15% / 3.0B tokens
  HuggingFaceFW/fineweb-edu, sample-10BT
  Educationally scored English FineWeb material.

Data-quality cautions:

  * revisions are not pinned;
  * cross-source deduplication is not run;
  * streamed source order is not explicitly shuffled before quota selection;
  * no final binary hash is recorded;
  * first three source row counts are unavailable in the completion manifest
    because tokenization resumed after interruption;
  * web data can contain errors, bias, personal information, unsafe material,
    benchmark content, and license obligations despite upstream filtering.

13.3 Modern 1B-1.7B orientation
-------------------------------

The SmolLM2 official card reports zero-shot base results:

  Model/base        HellaSwag  PIQA   WinoGrande  OpenBookQA
  ----------------------------------------------------------
  TLGM final*          37.9    65.7      51.9        31.6
  Llama-3.2-1B         61.2    74.8      57.8        38.4
  Qwen2.5-1.5B         66.4    76.1      59.3        40.0
  SmolLM2-1.7B         68.7    77.6      59.4        42.2

*TLGM numbers use the metric selection described above and a different local
protocol. The other row values are from SmolLM2's lighteval table.

Modern models benefit from trillions of tokens, larger/diverse vocabularies,
longer context, highly optimized Transformer blocks, curated math/code data,
preference optimization, and in Llama-3.2's case distillation. It is not
reasonable to expect the current 20B-token TLGM checkpoint to match them solely
because its registered parameter count is near 1B.


13.4 What can and cannot be inferred
------------------------------------

It is reasonable to infer that more high-quality pretraining and carefully
formatted reasoning SFT can improve TLGM. It is not justified to extrapolate
linearly from 20B to 300B/3T tokens or claim that equal token counts would erase
the architecture gap. TLGM's content-independent position mixing has a genuine
retrieval and generalization disadvantage relative to attention. Only a
controlled scaling experiment at several token budgets can separate data scale
from architecture quality.

15. SAFETY, LICENSING, AND MODEL-CARD LIMITATIONS
=================================================

This model should be treated as an experimental research model, not a reliable
ChatGPT replacement. It has no RLHF/DPO safety alignment, no moderation layer,
no retrieval grounding, no citation mechanism, and no factuality guarantee.

Expected limitations:

  * hallucinations and fabricated facts;
  * weak multi-step logic despite targeted SFT;
  * weak coding because code is not a meaningful part of the 20B final mix;
  * English-centric behavior;
  * only 1,024 tokens of context;
  * answer substitution and memorization from narrow repeated repair data;
  * poor calibrated uncertainty;
  * unsafe, biased, private, or copyrighted patterns inherited from public web
    and synthetic source data;
  * slow token-by-token generation without a cache;
  * no guarantee of robust behavior under adversarial prompts.

Dataset licenses are not uniform. Examples include ODC-By for SmolLM Corpus,
Wikipedia's CC BY-SA/GFDL terms, CC BY 4.0 for OpenMathInstruct-2, Apache 2.0
for OpenR1, MIT for UltraChat, and source-specific terms for Alpaca, Dolly,
FineWeb material, and underlying web documents. Redistribution requires a
separate legal/license review; public availability is not sufficient by itself.


16. PRIORITIZED REMEDIATION PLAN
===============================

Priority 0 - protect the active run:

  1. Install a dedicated reasoning systemd service without disabling UPS
     shutdown behavior.
  2. Add graceful signal checkpointing.
  3. Keep the current full checkpoint plus one previous full checkpoint.
  4. Do not change model/data semantics inside the already running process.

Priority 1 - correct SFT semantics before another major run:

  1. Expand multi-turn chats into per-assistant-turn samples.
  2. Preserve final answers and EOS for long math records.
  3. Filter/compact traces that cannot fit 1,024 tokens.
  4. Deduplicate UltraChat and all global instruction sources.
  5. Record truncation, target-token, duplicate, and source statistics.

Priority 2 - checkpoint and optimizer quality:

  1. Store resumable master weights in FP32 or BF16, never implicit FP16.
  2. Separate weight-decay and no-decay parameter groups.
  3. Add checkpoint schema/version, dtype, code revision, and artifact hashes.
  4. Add fallback/recovery tests using forced process termination.

Priority 3 - evaluation integrity:

  1. Run lm-evaluation-harness or lighteval with pinned versions and standard
     prompts in addition to the custom evaluator.
  2. Add ARC-Challenge, GSM8K exact-match, MMLU, SciQ, and a small generation
     quality set appropriate for 1B models.
  3. Decontaminate train data against all benchmark test/validation examples.
  4. Evaluate baseline final, latest reasoning, and best reasoning checkpoints
     with the identical pipeline.
  5. Report confidence intervals and both macro and per-task scores.

Priority 4 - architecture efficiency research:

  1. Pack lower-triangular sequence parameters.
  2. Explore content-conditioned gating that remains non-QKV and non-attention.
  3. Replace fixed absolute-only behavior with a relative or shift-stable
     non-attention position mechanism.
  4. Benchmark prefill and decode latency against a same-width Transformer.
  5. Test architecture scaling at 50M, 120M, 350M, and 1B under equal tokens.

Priority 5 - reproducibility and release:

  1. Pin dataset revisions and Python package versions.
  2. Hash tokenizer, token binary, JSONL datasets, configs, and checkpoints.
  3. Preserve an immutable run manifest and git/code archive.
  4. Publish exact licenses, data lineage, training curves, benchmark scripts,
     and known contamination.


17. REPRODUCTION SUMMARY
========================

To recreate an architecture-compatible model:

  * train or use the exact hashed 8,192 ByteLevelBPE tokenizer;
  * construct token and absolute position embeddings of width 2,048;
  * apply the shared 2,048 -> 8,192 -> 2,048 GELU token encoder and LayerNorm;
  * stack 27 blocks, each containing two learned causal 1,024 x 1,024 sequence
    matrices and one 2,048 -> 8,192 -> 2,048 GELU feature MLP;
  * use pre-normalization and residual connections in both block branches;
  * apply final LayerNorm and tied vocabulary projection;
  * train with one-token shifted cross entropy;
  * use the exact initialization rules in Section 4.5;
  * use AdamW, gradient clipping 1.0, the configured cosine schedule, and full
    sampler/RNG checkpointing;
  * use assistant-only targets for SFT;
  * implement the remediation items above for a new clean experiment rather
    than reproducing known data/checkpoint weaknesses.

Bit-for-bit reproduction is not currently possible from upstream identifiers
alone because source revisions and the 40GB binary hash are not recorded, CUDA
kernels may be nondeterministic, and pretraining crossed FP16/BF16 phases whose
exact transition is not encoded in checkpoint metadata.

19. FINAL ASSESSMENT
====================

TLGM-1B-1024 is a valid and technically interesting non-Transformer causal
language-model experiment. Its completed 20B-position pretraining and working
chat adaptation are substantial for a single-workstation project. The model's
best demonstrated strength is basic physical/science commonsense, while reading
comprehension, truthfulness, robust logic, and general chat intelligence remain
weak.

The active reasoning continuation is learning according to held-out loss, but
its current data formatting leaves significant capability on the table. The
most valuable next work is not blindly extending the same 120K steps. It is to
make long-answer and multi-turn supervision semantically correct, protect exact
checkpoint resumes, deduplicate and decontaminate data, and evaluate with a
standard pinned harness.

Even after those corrections, matching modern 1B-class models would require a
much larger and more diverse pretraining budget and may require architectural
changes that add content-dependent retrieval without violating the no-QKV/no-
Transformer design constraint. Equal parameter count does not imply equal
intelligence, and the present 20B-token budget is two to three orders of
magnitude below leading modern small-model training budgets.
